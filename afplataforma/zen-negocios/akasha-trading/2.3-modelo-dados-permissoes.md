# Akasha Trading · 2.3 Modelo de dados e permissões

**Status:** proposta de arquitetura. Não criar coleções nem publicar regras com base neste documento sem revisão do schema atual e das regras completas em produção.

## 1. Princípios

1. Uma identidade por pessoa no ecossistema Akasha; não criar login paralelo.
2. Separar dados pessoais, dados de trading, dados educacionais e dados institucionais.
3. Cada usuário controla seus registros pessoais; acesso de mentor/administrador é explícito, mínimo e auditável.
4. Dados de organizações devem ser isolados por organização e associação ativa.
5. Permissão deve ser aplicada no backend/Firestore Rules, não apenas na interface.
6. Não armazenar credenciais de corretoras, chaves privadas, seed phrases ou códigos de autenticação.
7. Não tratar dados de demonstração, estimativas ou cotações atrasadas como dados reais.
8. O Diário legado deve continuar utilizável durante a transição.

## 2. Identidade e acesso

A autenticação existente da AF utiliza Firebase Authentication e o UID como identificador. A integração proposta reutiliza o UID autenticado, sujeito à verificação do fluxo atual e das regras publicadas.

### Matriz de perfis

| Perfil | Escopo permitido |
|---|---|
| Visitante | Conteúdo público e ferramentas explicitamente abertas |
| Conta gratuita | Perfil Trading próprio, trilhas abertas e diário pessoal |
| Premium | Recursos adicionais definidos por entitlement ativo |
| Membro AF/Legado | Recursos institucionais concedidos pela AF, sem acesso automático a dados privados de terceiros |
| Mentor/consultor | Dados compartilhados por vínculo e finalidade autorizada |
| Administrador Trading | Gestão operacional do produto, sem acesso irrestrito por padrão |
| Serviço backend | Operações técnicas específicas, com credencial de serviço e trilha de auditoria |

Um usuário pode acumular papéis. O papel não substitui a checagem de propriedade, organização, status ativo e finalidade de acesso.

## 3. Modelo lógico proposto

Coleções sugeridas no Firestore. Os nomes são uma proposta nova e não devem ser confundidos com coleções legadas como `taAccess`, `taTools`, `afTools` ou `afCalls`.

| Caminho lógico | Finalidade | Escrita |
|---|---|---|
| `tradingProfiles/{uid}` | Preferências e perfil de uso não sensível | Usuário dono; campos permitidos |
| `tradingEntitlements/{uid}` | Plano, recursos e validade de acesso | Backend/admin autorizado |
| `tradingProgress/{uid}/courses/{courseId}` | Progresso educacional | Usuário dono |
| `tradingWatchlists/{uid}/assets/{assetId}` | Ativos acompanhados e tese pessoal | Usuário dono |
| `tradingRiskProfiles/{uid}` | Preferências e limites declarados de risco | Usuário dono; validação de campos |
| `tradingJournals/{uid}/trades/{tradeId}` | Registros pessoais de operações | Usuário dono |
| `tradingJournals/{uid}/notes/{noteId}` | Notas associadas ao diário | Usuário dono |
| `tradingPortfolios/{uid}/items/{itemId}` | Carteiras de acompanhamento/estudo | Usuário dono |
| `tradingReports/{uid}/reports/{reportId}` | Relatórios derivados e snapshots | Backend ou usuário, conforme tipo |
| `tradingOrganizations/{orgId}` | Cadastro mínimo da organização | Admin autorizado |
| `tradingOrganizations/{orgId}/members/{uid}` | Vínculo e papel do membro | Admin da organização |
| `tradingOrganizations/{orgId}/workspaces/{workspaceId}` | Dados explicitamente compartilhados | Membros autorizados |
| `tradingAudit/{eventId}` | Eventos críticos de acesso/admin/migração | Backend somente |

O caminho definitivo pode mudar após inspeção de coleções existentes, volume esperado, consultas e regras. Não armazenar o mesmo registro em múltiplos lugares sem uma fonte de verdade definida.

## 4. Campos mínimos recomendados

### Registro de operação

- `id`: identificador estável, preferencialmente UUID.
- `ownerUid`: UID proprietário.
- `assetSymbol`: símbolo informado.
- `direction`: long/compra ou short/venda, com enum validado.
- `resultAmount`: valor numérico e moeda explícita.
- `plannedRiskAmount`: opcional.
- `emotion`, `planAdherence`, `stopUsed`: campos opcionais normalizados.
- `lesson`: texto com limite de tamanho.
- `occurredAt`: timestamp da operação.
- `createdAt`, `updatedAt`: timestamps do sistema.
- `source`: legacy-local, web ou import.
- `schemaVersion`: versão do formato.

Não inferir preço de entrada, preço de saída, quantidade, taxas ou lucro percentual quando o diário legado não os registra.

### Nota

- `id`, `ownerUid`, `category`, `body`, `createdAt`, `updatedAt`, `source`, `schemaVersion`.

### Perfil e entitlement

Manter dados de perfil separados de dados comerciais. Valores pagos, condições comerciais e dados de cobrança não devem ser expostos em documentos legíveis pelo próprio usuário sem necessidade. A fonte de verdade de cobrança deve permanecer no sistema de pagamentos autorizado, com o Firestore contendo somente o estado mínimo necessário para autorização.

## 5. Regras de autorização

- Usuário autenticado só lê/escreve seus próprios registros pessoais.
- Acesso premium depende de entitlement ativo validado no servidor ou em regra confiável.
- Mentor só acessa dados de um mentorado mediante vínculo explícito, finalidade e autorização registrada.
- Admin não recebe leitura irrestrita de dados financeiros pessoais por simples papel de interface.
- Membros de organização só acessam workspace da organização à qual pertencem e enquanto vínculo estiver ativo.
- Coleções de auditoria, entitlements e dados derivados protegidos: escrita somente backend/admin restrito.
- Negar por padrão qualquer caminho não declarado.
- Validar tipo, tamanho, campos permitidos, timestamps e transições de estado.
- Não aceitar `ownerUid`, `role`, `approved`, `active` ou `plan` definidos pelo cliente como prova de autorização.

## 6. Migração e compatibilidade

O modelo precisa suportar registros importados do diário local com `source=legacy-local`, identificador de importação e versão de schema. A importação deve ser idempotente: reexecutar o mesmo lote não pode duplicar registros.
